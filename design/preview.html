Multi-page support

Seven states, built on the shipped tokens. This is the Step 1 design preview — index.html is untouched and nothing here is wired to a database.

State 1

Single page — the feature is not present

Not a greyed-out strip, not one lonely tab, not a “1 page” chip. Nothing. Section 1.1, expertise-reversal: scaffolding that helps a novice becomes extraneous load for everyone else, and a tab strip with one tab is chrome explaining a feature nobody is using. Discovery lives in the overflow menu. This is also exactly what an unmigrated database renders, which is why someone who never migrates barely notices this shipped.

States 2 & 3

Multi-page, and switching between pages

The strip sits inside the existing header box, under the wordmark, in space the left block already wasted. It adds no vertical band and pushes nothing down. “+ Add application” stays the only filled control in the interface (section 1.2 — restraint is what gives the one emphasis its force), so tabs are text plus a 2px underline: quieter than the sync chip.

Click the tabs, or focus one and use the arrow keys. The swap is unanimated and the underline does not slide — section 3.1, “when NOT to animate”: high-frequency, low-novelty interactions should often appear without motion, and after the hundredth switch a travelling underline is a tax on perceived speed. There is also no request to hide: every page’s rows arrive in the query that already runs, so switching is a filter over data already in hand.

State 4

State 5

Deleting a page

Deletion moves the page’s applications — live and trashed alike — to the first remaining page. Nothing is destroyed, so the confirmation says so rather than performing danger it cannot deliver (Rams 6, section 1.2 material honesty). A dialogue that shouts about consequences that do not exist teaches people to click through dialogues. The count is real, read from the rows in hand.

State 6

Unmigrated database

This is the existing MigrationNotice with a longer MIGRATION_SQL — not a second mechanism. Detection is one string: page_id joins SELECT_COLUMNS, so asking for the columns is still the schema check, isMissingColumn still catches 42703, and the loader still re-fetches with select("*") so the reader keeps every application they own.

The ordering rule that makes this safe: nothing queries tracker_pages until the page_id probe returns clean. That table does not exist here, and its absence raises 42P01, which isMissingColumn does not recognise — it would surface as a raw Postgres error, the one outcome the brief forbids. The two queries sit in the same await chain, so they cannot race.

Your database needs one update

This version adds pages — separate collections of applications in one account. Run the script below in SQL Editor → New query, then reload. It only adds things, so nothing you already have is touched. 

create table if not exists public.tracker_pages (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null default auth.uid()
               references auth.users(id) on delete cascade,
  name       text not null default 'Applications',
  sort_order bigint not null default 0,
  created_at timestamptz not null default now()
);

create index if not exists tracker_pages_user_idx
  on public.tracker_pages (user_id, sort_order);

alter table public.tracker_pages enable row level security;

drop policy if exists "owner full access pages" on public.tracker_pages;
create policy "owner full access pages"
  on public.tracker_pages for all to authenticated
  using (auth.uid() = user_id) with check (auth.uid() = user_id);

grant select, insert, update, delete on public.tracker_pages to authenticated;

-- Nullable on purpose: a row whose page is gone must still be visible.
alter table public.applications
  add column if not exists page_id uuid
    references public.tracker_pages(id) on delete set null;

create index if not exists applications_page_idx
  on public.applications (user_id, page_id, sort_order);

-- One default page per account, and every existing application put on it.
insert into public.tracker_pages (user_id, name, sort_order)
select distinct a.user_id, 'Applications', 0
  from public.applications a
 where not exists (
   select 1 from public.tracker_pages p where p.user_id = a.user_id
 );

update public.applications a
   set page_id = (
     select p.id from public.tracker_pages p
      where p.user_id = a.user_id
      order by p.sort_order, p.created_at
      limit 1
   )
 where a.page_id is null;

State 7

Mobile

A horizontal tab strip is the wrong control at phone width: it truncates, scrolls sideways off screen, and the tab you want is the one you cannot see. Below lg the strip becomes one full-width button naming where you are, opening a menu of every page — recognition over recall (section 1.1), the largest tap target the layout allows, and it does not degrade as pages are added. It is the existing OverflowMenu primitive, so there is no new mechanism and no new dependency. Google Sheets on a phone uses a sheet-list button for the same reason.

After build

What gets re-measured, and what fails the build

The header gains a second line, which changes what sits above the rows — and the R1 round proved that layout above the rows can move their edges. So the invariant is restated here to be checked rather than assumed:

One element owns background, border-radius and box-shadow. The hairline is an inset ring on that same element. No clipping ancestor.

  • Corner probe — four corners of a row card, pointer parked away from the grid so --hover is inactive. That second clause is the round-4 detector fault; it is not repeated.
  • Bottom-edge probe — sampled below the last card with a window smaller than the current row gap, so it measures the card’s own shadow rather than the next card’s edge.
  • Header height — measured before and after. Section 5.3 claims the strip adds no vertical band; if it does, the placement is wrong and gets revised, not shipped.
  • Switch cost — React commit duration across two pages of ~50 rows. Must not exceed one frame at 60Hz.
  • Ten inviolable behaviours — individually, pass or fail each. #9 re-tested specifically with two pages: adding a row clears the stage filter and must not switch pages.

If either shadow probe moves, the fix is the layout — not box-shadow values.

Reorder

Springboard-style reordering

Grab a handle and drag. The row you hold is attached to the pointer with no transition — any easing between finger and row reads as lag (§3.1, immediately responsive). Everything it displaces slides into its new slot. That asymmetry is what makes the iOS effect read correctly.

Transform only, so nothing re-lays-out mid-flight — which is also why the corners and shadow hold throughout: a transformed box paints its own border-radius and box-shadow. cubic-bezier(0.22, 1, 0.36, 1), the dossier's smooth approximated spring, at 220ms — under the ~300ms ceiling §3.1 sets. The energetic (0.34, 1.56, …) curve overshoots, and four rows springing past their slots at once reads as sloppy.

Under prefers-reduced-motion the reorder still happens; the rows simply arrive.

Paste to create

The entry point

Paste sits beside the primary action, not inside the overflow menu. Both are the same intent — create an application — differing only in whether the advert is already on your clipboard, and section 2.1 keeps one decision in one fixation zone rather than splitting it across two places. The overflow menu holds configuration; a creation action filed under settings is a category error and undiscoverable besides. It stays subordinate by the one mechanism that matters here: no accent fill. The single filled control is what makes the primary action unambiguous (section 1.2), so anything unfilled beside it reads as secondary without being shrunk or greyed — contrast doing compositional work rather than decorative (section 2.3).

State 2

Review — everything found

A field the parser is sure of carries no caption at all. That is the point: captions appear only where the evidence is weak, so the eye lands on exactly what needs checking instead of scanning five equally-decorated rows. Uncertainty is expressed by adding information — which rule fired — not by adding colour, so it survives greyscale, print and colour blindness, and it reaches a screen reader through aria-describedby (section 4.2: show provenance, let users intervene).

State 4

The duplicate warning

Matching ignores case, accents, punctuation and legal form — Bloomberg L.P., BLOOMBERG LP and bloomberg are one company. It warns and never blocks: two roles at one employer is normal, and the user knows better than the parser. Shown during review, before the row exists, because a warning after creation is just a chore.

You already have Bloomberg L.P. — Equity Research on this page. Two roles at one company is perfectly normal; this is only a heads-up.

State 5

Mobile

Pasting on a phone is the likeliest case, not the degraded one — people browse jobs on a phone. So the dialog is a full-bleed sheet rather than a shrunken desktop card: edge to edge, square where the screen ends, review fields at full width. Type in the textarea and the review inputs is forced to 16px here: below that, iOS Safari zooms the viewport on focus and does not zoom back, so the first tap would leave the reader scrolled sideways through a dialog they had not read. The desktop scale is 12.48px, which is precisely the trap.
